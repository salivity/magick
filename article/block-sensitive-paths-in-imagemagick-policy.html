Block Sensitive Paths in ImageMagick Policy

Securing an ImageMagick installation requires restricting which parts of the filesystem the utility can read from or write to, preventing Server-Side Request Forgery (SSRF) and Local File Inclusion (LFI) vulnerabilities. This guide explains how to edit ImageMagick's policy.xml configuration to explicitly deny access to sensitive system directories such as /etc, /proc, and /sys, ensuring internal files cannot be processed or leaked through image manipulation operations.

Locate the Policy Configuration

ImageMagick controls operational permissions through its security policy file, policy.xml. Depending on your operating system and ImageMagick version, this file is typically located in one of the following directories:

  • /etc/ImageMagick-7/policy.xml
  • /etc/ImageMagick-6/policy.xml
  • /usr/local/etc/ImageMagick-7/policy.xml

You can verify the active configuration path by running:

magick -list configure | grep -i "configure_path"
# Or for ImageMagick 6:
convert -list configure | grep -i "configure_path"

Configure Path Domain Policies

ImageMagick provides the path domain directive to control filesystem access based on path patterns and permission rights (read, write, execute, or none).

To block access to /etc and other sensitive paths, open policy.xml in an editor with administrative privileges:

sudo nano /etc/ImageMagick-7/policy.xml

Locate the <policymap> element and insert rules defining zero rights (rights="none") for sensitive patterns.

Method 1: Explicit Blacklisting

To explicitly deny reading or writing to /etc and critical system directories, add the following policies inside the <policymap> block:

<policymap>
  <!-- Deny access to critical system directories -->
  <policy domain="path" rights="none" pattern="/etc/*"/>
  <policy domain="path" rights="none" pattern="/proc/*"/>
  <policy domain="path" rights="none" pattern="/sys/*"/>
  <policy domain="path" rights="none" pattern="/root/*"/>
  <policy domain="path" rights="none" pattern="/var/run/*"/>
</policymap>

Method 2: Whitelisting (Recommended)

A blacklist can often be bypassed using symlinks or relative paths if not comprehensively mapped. The most secure approach is a default-deny policy that blocks all filesystem paths and only permits specific, required operational directories (such as temporary processing folders and application upload directories):

<policymap>
  <!-- Deny access to all paths by default -->
  <policy domain="path" rights="none" pattern="*"/>

  <!-- Explicitly allow temporary and application-specific directories -->
  <policy domain="path" rights="read|write" pattern="/tmp/*"/>
  <policy domain="path" rights="read|write" pattern="/var/www/uploads/*"/>
</policymap>

Policy rules are evaluated in the order they appear. Place broad restrictions first and specific whitelist exceptions afterward if using whitelisting.

Disable Indirect File Access

ImageMagick supports filename references inside image files (such as text-rendering primitives or SVG files referencing external entities) that could attempt to read local files. In addition to path restrictions, disable vulnerable coder modules and protocols that allow indirect file reading:

<policy domain="coder" rights="none" pattern="{TEXT,SHOW,LABEL,WIN,MVG,MSL,EPHEMERAL,URL,FTP,HTTP,HTTPS}"/>

Verify the Configuration

After saving the changes to policy.xml, confirm that the rules are active:

magick -list policy

Test the restriction by attempting to read a file from /etc into an output format:

magick /etc/passwd output.png

If the policy is configured correctly, ImageMagick terminates execution and outputs an error:

magick: not authorized `/etc/passwd' @ error/constitute.c/ReadImage/412.
