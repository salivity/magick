Disable ImageMagick Coders to Reduce Attack Surface

This article outlines how to restrict image coders in ImageMagick at both build time and runtime to minimize the software's attack surface. By disabling dynamic modules during compilation and restricting unnecessary formats via security policies, system administrators can prevent exploitation of vulnerable delegates and complex file parsers.

The ./configure Option: --without-modules

At build time, the primary ./configure option to disable dynamic coder loading is:

./configure --without-modules

By default, ImageMagick can build coders as dynamically loadable shared objects. Supplying --without-modules disables this modular loading mechanism, forcing coders to be statically linked. This prevents ImageMagick from attempting to dynamically find and load arbitrary coder modules at runtime, substantially reducing the vector for loading rogue or untrusted decoder plugins.

To eliminate support for specific third-party libraries and formats altogether during compilation, you can append specific delegate-disabling flags to ./configure:

  • --without-ps: Disables PostScript support.
  • --without-pdf: Disables PDF handling.
  • --without-wmf: Disables Windows Metafile support.
  • --without-x: Disables the X Window System delegate.

Runtime Coder Disabling: policy.xml

While --without-modules eliminates dynamic module loading at compile time, completely turning off built-in or unused image coders is natively achieved via ImageMagick’s runtime configuration file, policy.xml.

To disable unused or high-risk coders (such as those that delegate parsing to external tools like Ghostscript), set the domain="coder" rights to none within <policymap>:

<policymap>
  <!-- Disable specific vulnerable coders -->
  <policy domain="coder" rights="none" pattern="EPHEMERAL" />
  <policy domain="coder" rights="none" pattern="URL" />
  <policy domain="coder" rights="none" pattern="HTTPS" />
  <policy domain="coder" rights="none" pattern="MVG" />
  <policy domain="coder" rights="none" pattern="MSL" />
  <policy domain="coder" rights="none" pattern="TEXT" />
  <policy domain="coder" rights="none" pattern="SHOW" />
  <policy domain="coder" rights="none" pattern="WIN" />
  <policy domain="coder" rights="none" pattern="PLT" />
  <policy domain="coder" rights="none" pattern="PS" />
  <policy domain="coder" rights="none" pattern="PDF" />
</policymap>

To enforce an explicit whitelist instead of a blacklist, block all coders first and explicitly permit only the formats required by your application:

<policymap>
  <!-- Block all coders by default -->
  <policy domain="coder" rights="none" pattern="*" />
  
  <!-- Explicitly allow only required formats -->
  <policy domain="coder" rights="read|write" pattern="{PNG,JPEG,WEBP}" />
</policymap>

Security Impact

ImageMagick supports over 200 formats, many of which execute external binaries, parse complex legacy specifications, or handle network requests. Disabling dynamic modules with --without-modules and restricting formats to an explicit whitelist in policy.xml eliminates common vulnerability classes—including arbitrary command execution (such as ImageTragick), server-side request forgery (SSRF), and memory safety bugs—without affecting standard image processing operations.
