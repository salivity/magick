How ImageMagick Parses Coder Prefixes in Filenames

When ImageMagick processes an input or output target, it allows users to explicitly specify the image format using coder prefixes such as png: or jpg: prepended to the filename. This article explains the internal parsing mechanism ImageMagick uses to identify these prefixes, isolate the coder specification, override standard file signature (magic byte) and extension detection, and route the image stream to the appropriate coder module.

String Tokenization and Colon Delimitation

The parsing process begins during the initialization of the ImageInfo structure, typically inside MagickCore's SetImageInfo() function. ImageMagick scans the input string from left to right looking for a colon (:) separator.

When a colon is encountered, the substring preceding it is evaluated as a potential coder or protocol name. The parser splits the full input path into two primary components:

  1. The Prefix (Coder/Protocol): The text preceding the colon (e.g., png in png:input.dat).
  2. The Target Path: The text succeeding the colon, which represents the actual file system path, stream descriptor, or delegate parameter (e.g., input.dat or - for standard input).

If the string contains multiple colons (such as in Windows absolute paths like C:\images\test.png), ImageMagick applies sanity checks. Single-letter prefixes followed by a backslash or slash (e.g., c:) are recognized as Windows drive letters and are ignored by the coder parsing logic.

Registry Lookup via GetMagickInfo

Once a candidate prefix is isolated, ImageMagick does not immediately assume it is a valid format. Instead, it queries its internal coder registry using the GetMagickInfo() function:

  1. The extracted prefix is converted to uppercase to perform a case-insensitive lookup.
  2. ImageMagick searches its registered table of MagickInfo structures, which define all available read/write delegates, built-in formats, and pseudoclass handlers.
  3. If a match is found (for example, PNG or JPEG), ImageMagick populates the magick member of the ImageInfo structure with that format name.

If the prefix matches a protocol handler (such as http:, https:, or fd:), the string is routed to the corresponding I/O sub-handler rather than treated strictly as an encoding format.

Bypassing Automatic Format Detection

Under normal circumstances, ImageMagick determines an image's format using a two-tier fallback system:

  • Magic Bytes: Inspecting the initial header bytes of the file content.
  • File Extension: Falling back to the file extension at the end of the filename if header sniffing fails.

When an explicit prefix is parsed and set in ImageInfo->magick, this default detection sequence is bypassed. During the subsequent call to ReadImage():

  1. ImageMagick checks if image_info->magick is non-empty.
  2. If set, it skips header sniffing and directly invokes the registered decoding routine (the ReadImage function pointer defined within the corresponding coder module, such as ReadPNGImage for png:).
  3. The remaining portion of the filename (everything after the colon) is used strictly to locate the bytes on disk or in memory.

Handling Modifiers and Sub-Image Indexes

Coder prefix parsing occurs before embedded read modifiers or frame specifiers are handled. Once the prefix has been extracted and assigned to ImageInfo->magick, ImageMagick continues parsing the remaining path for bracketed sub-image expressions (such as [0] in gif:animation.gif[0]) and canvas geometry settings. The coder itself remains locked to the explicit prefix defined at the beginning of the string.
