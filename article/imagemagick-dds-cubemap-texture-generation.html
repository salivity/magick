ImageMagick DDS Cubemap Texture Generation

This article provides an overview of how ImageMagick constructs cube map textures in DirectDraw Surface (DDS) format, detailing input image requirements, internal encoding processes, header flag management, and command-line implementation.

Face Ordering and Input Requirements

A standard DDS cubemap consists of six distinct square sub-images representing the interior faces of a cube. When using ImageMagick, you must supply these six faces as an ordered sequence of frames. ImageMagick expects the input textures to adhere to the Microsoft DirectX cubemap coordinate conventions, arranged in the following sequence:

  1. Positive X (+X): Right face
  2. Negative X (-X): Left face
  3. Positive Y (+Y): Top face
  4. Negative Y (-Y): Bottom face
  5. Positive Z (+Z): Forward/Front face
  6. Negative Z (-Z): Backward/Back face

Each face must be square and share identical dimensions, ideally with power-of-two resolutions (e.g., 512×512, 1024×1024, or 2048×2048) to maintain GPU compatibility.

DDS Header and Capability Flags

When writing to a .dds destination file with cubemap parameters, ImageMagick constructs a standard 128-byte DDS header (DDS_HEADER). For cubemaps, ImageMagick updates the secondary capability member, dwCaps2, setting the DDSCAPS2_CUBEMAP flag (0x00000200).

To mark all six faces as valid and present within the container, ImageMagick enables the individual face flags or applies the composite DDSCAPS2_CUBEMAP_ALLFACES flag (0x0000FC00), which includes:

  • DDSCAPS2_CUBEMAP_POSITIVEX (0x00000400)
  • DDSCAPS2_CUBEMAP_NEGATIVEX (0x00000800)
  • DDSCAPS2_CUBEMAP_POSITIVEY (0x00001000)
  • DDSCAPS2_CUBEMAP_NEGATIVEY (0x00002000)
  • DDSCAPS2_CUBEMAP_POSITIVEZ (0x00004000)
  • DDSCAPS2_CUBEMAP_NEGATIVEZ (0x00008000)

Compression and Pixel Formatting

ImageMagick encodes each face sequentially into the DDS data stream using the coder specified by command-line defines. Depending on your configuration, ImageMagick processes the pixel buffers using one of several formats:

  • Uncompressed RGBA: Stores raw pixel channels using 8 bits per channel (32-bit format).
  • DXT1 / BC1: Compresses 4×4 pixel blocks into 64-bit chunks, ideal for diffuse environment maps without alpha data.
  • DXT5 / BC3: Employs interpolated alpha blocks alongside color compression, suitable for maps requiring fine alpha transitions.

ImageMagick serializes the full data payload for face zero before beginning the payload for face one, repeating until all six faces are written.

Mipmap Chains in Cubemaps

If mipmap generation is requested, ImageMagick does not filter the six faces as a single combined texture. Instead, it generates a complete, descending mipmap chain independently for each individual face down to a 1×1 pixel dimension.

In the serialized DDS file, each face is immediately followed by its complete set of mip levels before the file advances to the next cubemap face:

[Face +X Level 0] -> [Face +X Mip 1] -> ... -> [Face +X Mip N] -> [Face -X Level 0] -> ...

The dwCaps field is updated with DDSCAPS_MIPMAP (0x00400000), and dwMipMapCount stores the total number of levels per face.

Command-Line Implementation

To generate a DDS cubemap in ImageMagick, pass the six individual face textures in the correct DirectX order and specify the cubemap definition:

magick posx.png negx.png posy.png negy.png posz.png negz.png -define dds:cubemap=true output.dds

To include automatic mipmap creation and select DXT1 compression, append the corresponding defines:

magick posx.png negx.png posy.png negy.png posz.png negz.png -define dds:cubemap=true -define dds:compression=dxt1 -define dds:mipmaps=from-filter output.dds

ImageMagick packages the frames, downsamples the mip levels if designated, compiles the pixel data, writes the header metadata, and exports a fully compliant DDS cubemap for real-time 3D rendering engines.
