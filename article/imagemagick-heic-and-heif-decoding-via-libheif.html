ImageMagick HEIC and HEIF Decoding via libheif

ImageMagick processes High Efficiency Image Format (HEIF) and High Efficiency Image Coding (HEIC) files by integrating with libheif as an external delegate library. Because HEIF is a complex container format enclosing compressed media streams, ImageMagick does not decode the raw bitstreams directly. Instead, it delegates container parsing, track demuxing, metadata extraction, and hardware/software decompression to libheif, which in turn utilizes underlying codec decoders like libde265 or dav1d to return standard raster pixel data.

The Delegate Architecture

ImageMagick relies on a modular architecture where specific file formats are mapped to coder modules. When ImageMagick encounters a file with .heic, .heif, or corresponding MIME types, it invokes its internal heic.c coder module.

This module acts as an abstraction bridge to the C/C++ API of libheif. ImageMagick passes the file stream or memory buffer to libheif, which manages the ISOBMFF (ISO Base Media File Format) box structure used by HEIF containers.

The Step-by-Step Decoding Pipeline

  1. Format Identification and Box Parsing
    libheif inspects the initial bytes to confirm compatibility, checking the ftyp (file type) box for brand identifiers such as heic, heix, mif1, or msf1. It parses the file’s structural boxes to identify primary images, secondary image tracks, depth maps, and thumbnails.

  2. Codec Invocation
    The HEIF container wraps compressed video frame payloads. To decompress these payloads, libheif calls dedicated codec plugins:

    • HEVC/H.265: Decompression is handled by libde265 or x265.
    • AV1 (AVIF): Decompression is passed to dav1d, libaom, or svt-av1.

  3. Pixel Reconstruction and Color Space Conversion
    The underlying codec outputs raw uncompressed image data, typically formatted in planar YUV color spaces (such as YUV420p, YUV422p, or YUV444p) across varying bit depths (8, 10, or 12 bits per channel). libheif handles the conversion from YUV to interleaved RGB or RGBA, adjusting for color range expansions (full vs. limited range).

  4. Transfer to ImageMagick Quantum Structures
    ImageMagick receives the unpacked RGB/RGBA buffers and converts the pixel data into its internal Quantum memory arrays, matching the compilation depth (Q8, Q16, or Q32) and assigning alpha channels if transparency masks or auxiliary tracks exist.

  5. Metadata and Profile Preservation
    During container parsing, libheif locates uncompressed metadata payloads stored inside the meta box:

    • EXIF and XMP Data: Extracted as raw binary blobs and attached as string attributes/profiles to ImageMagick’s internal image structure.
    • ICC Color Profiles: Retrieved from the colr box and embedded directly into the ImageMagick image instance to ensure accurate color management.

Multi-Frame and Animation Handling

HEIF files can store image sequences, bursts, or multi-resolution image pyramids. ImageMagick queries libheif for the total count of image items:

  • For single image requests, it reads only the primary image handle (heif_context_get_primary_image_handle).
  • For multi-frame requests or sequence conversions, ImageMagick iterates over the item IDs (heif_context_get_list_of_top_level_image_IDs), instantiating a distinct sub-image in its internal image list for each item.

System Verification

For ImageMagick to successfully decode HEIC/HEIF files, it must be compiled with --with-heic support and have libheif (along with a decoder like libde265) installed on the host system. Support can be verified from the command line:

magick identify -list format | grep -i heic

A properly configured environment returns HEIC with r (read) and w (write) permissions, confirming that the libheif delegate is actively routing decode operations.
