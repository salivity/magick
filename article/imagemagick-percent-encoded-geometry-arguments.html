ImageMagick Percent-Encoded Geometry Arguments

This article examines how ImageMagick processes geometry arguments that contain percent-encoded characters, outlining the behavior of its internal parser and the implications for web applications. ImageMagick does not automatically decode percent-encoded strings within geometry parameters, meaning sequences such as %20 or %21 are treated as literal text and standard geometry modifiers rather than decoded characters.

The Role of the Geometry Parser

ImageMagick relies on internal routines such as ParseGeometry() and ParseMetaGeometry() to interpret geometry strings passed to operators like -resize, -crop, -extent, and -thumbnail. The parser adheres to a strict syntax grammar designed to recognize dimensions, offsets, and explicit modifier flags:

  • x (separator between width and height)
  • + and - (coordinate offsets)
  • % (percentage modifier)
  • ! (ignore aspect ratio)
  • ^ (fill area)
  • > and < (conditional enlargement or reduction)

Because this parser operates directly on raw strings without an integrated URL-decoding phase, it does not treat a percent sign followed by two hexadecimal digits (%XX) as an escape sequence.

Evaluation of Percent Signs in Geometry Strings

In standard ImageMagick syntax, the % character denotes that a given dimension represents a percentage rather than an absolute pixel value. When a percent-encoded character is passed into a geometry argument, ImageMagick evaluates the % as this scaling flag.

For example, consider the percent-encoded string 500x500%21, where %21 represents the URL-encoded form of an exclamation mark (!):

  1. The parser processes 500x500.
  2. It encounters the % symbol, flagging the height or overall dimension as a percentage value.
  3. It encounters the remaining characters 21.
  4. Because 21 appears after the dimension and modifier flags where an offset (+X+Y) is expected, the parser fails to parse the string correctly, or it assigns unexpected offset values.

Similarly, an encoded space (%20) results in the parser seeing a percentage flag followed by the number 20, rather than whitespace. If a geometry string contains characters that cannot be reconciled with the expected syntax, ImageMagick typically issues a warning, falls back to default values, or ignores the malformed segment entirely.

Interaction with Web Applications and APIs

Issues regarding percent-encoded geometry usually arise when ImageMagick is integrated into dynamic image processing pipelines, microservices, or URL-based media servers. In these architectures, geometry parameters often originate from URL query strings or path parameters.

  • Implicit Decoding by Frameworks: Most modern web frameworks automatically decode URL-encoded components before passing them to application handlers. If decoded properly, a string such as 100x100%21 becomes 100x100! before it reaches the ImageMagick wrapper or command-line interface.
  • Double-Encoded Inputs: If an input is double-encoded (e.g., %2521), the application may decode it once to %21. When this string is passed to ImageMagick, the tool will encounter the literal %21 and fail to apply the intended aspect-ratio override.
  • Security and Validation: Passing unsanitized, raw query parameters containing percent signs to shell-based ImageMagick commands introduces parsing errors and unexpected behavior. Geometry inputs should always be validated against an allowlist pattern (such as ^[0-9]+%?[xX]?[0-9]*%?[!><^]?$) prior to invocation.
