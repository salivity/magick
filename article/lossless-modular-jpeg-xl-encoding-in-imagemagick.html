Lossless Modular JPEG XL Encoding in ImageMagick

ImageMagick achieves lossless JPEG XL (JXL) compression by routing image data through the reference library libjxl to generate a dedicated modular bitstream within the JXL format. Unlike the DCT-based VarDCT mode used for lossy photographic content, lossless encoding automatically switches the architecture to JPEG XL’s Modular mode. This pipeline relies on reversible color transforms, localized spatial predictors, and Asymmetric Numeral System (ANS) entropy coding to compress raster data bit-for-bit without loss, packaging the results into a compliant raw codestream or an ISO Base Media File Format (ISOBMFF) container.

The Role of ImageMagick and libjxl

ImageMagick does not implement the core JPEG XL mathematical transforms natively. Instead, its internal delegate architecture acts as an abstraction layer that interfaces with libjxl.

When a user invokes a command such as magick input.png -quality 100 output.jxl, ImageMagick recognizes the maximum quality setting and translates this into libjxl API calls. Specifically, it configures the encoder with a Butteraugli distance of 0.0 and triggers the lossless flag (JxlEncoderSetFrameLossless). This configuration forces the underlying encoder to bypass the lossy VarDCT engine entirely and direct all pixel processing to the Modular engine.

Users can control modular performance characteristics directly from ImageMagick via definitions:

  • -define jxl:effort=[1-9]: Adjusts the computational heuristics for spatial tree generation and context modeling.
  • -define jxl:modular=1: Manually mandates the modular pipeline, even if working at non-default settings.

The Modular Engine Architecture

The JPEG XL Modular engine is an integer-based coding framework designed specifically for lossless graphics, non-photographic assets, alpha channels, and responsive sub-resolutions.

When ImageMagick passes uncompressed pixel channels (such as 8-bit, 16-bit, or floating-point RGBA buffers) to libjxl, the modular pipeline processes the data through a series of discrete, reversible stages:

1. Reversible Color Transformations (RCT)

Standard color conversions (like lossy RGB to YCbCr) introduce rounding errors and floating-point drift. The Modular engine instead applies Reversible Color Transforms, such as reversible YCoCg-R, or derives dynamic, data-dependent color transforms using decision trees. This step decorrelates the color channels without altering the underlying integer fidelity.

2. Squeeze Transforms

The modular mode can optionally apply reversible Haar-like transforms across horizontal and vertical dimensions (the "Squeeze" transform). This breaks the image into progressive resolution layers. While frequently disabled in pure lossless operations to minimize overhead, higher effort levels explore this step to improve spatial correlation in specific channel configurations.

3. Spatial Prediction

To remove intra-channel redundancy, the modular engine uses predictive coding on the decorrelated channels. Rather than storing literal pixel values, the encoder predicts the value of the current pixel based on its previously encoded neighbors (North, West, North-West) and records only the residual error (difference).

Common predictors deployed by the modular engine include:

  • Zero/None: Useful for high-entropy or noisy regions.
  • Clamped Gradient (Median): Calculates \(West + North - NorthWest\), clamping the result to maintain edge boundaries.
  • Weighted/Adaptive Predictors: Dynamically evaluated predictors selected via decision trees that adjust to gradients and directional edges.

4. Context Trees and Entropy Coding

The prediction residuals are processed using Asymmetric Numeral Systems (ANS), a modern alternative to traditional Huffman or arithmetic coding that pairs high throughput with optimal compression ratios.

The modular engine constructs binary decision trees (Modular Trees) based on local properties—such as the gradient magnitude or values of neighboring pixels. These trees partition residuals into distinct contexts, allowing the ANS encoder to model the probability distribution of errors accurately. Higher effort levels configured in ImageMagick grant the tree search algorithm more time to find optimal splitting points, significantly reducing final file sizes.

Packaging into the JXL Container

Once the modular stream is finalized, ImageMagick packages the encoded bitstream into one of two container structures:

  1. Bare Codestream: If the image contains no external metadata (such as Exif, XMP, or custom color profiles), the stream is written directly with standard JXL framing markers (0xFF0A).
  2. ISOBMFF Box-Based Container: When metadata preservation is required, ImageMagick creates a standard box structure starting with a JXL file header box (ftyp jxl ). The raw modular codestream is placed within a jbrd (JPEG reconstruction data) or jxli / jxlc (codestream) box, while Exif, XMP, and ICC profiles are encapsulated within dedicated metadata boxes (Exif, xml , and standard color specification markers).

This modular container workflow ensures that regardless of whether the source is a high-depth medical scan, digital art, or a simple photographic file, ImageMagick delivers a standard-compliant, fully lossless representation.
