Mogrify vs Convert: ImageMagick Batch Speed

When processing large batches of images, ImageMagick's mogrify is significantly faster than convert when convert is used within standard shell loops. This article examines the execution speed differences between mogrify and convert, breaks down the technical reasons behind the performance gap, and explains how process overhead impacts batch image workflows.

The Fundamental Architectural Difference

The primary reason for the execution speed difference lies in how operating systems handle process execution:

  • convert (Individual Process Model): Traditional batch scripts process files using a loop (such as a Bash for loop) that invokes convert once per image. For a directory of 1,000 images, the operating system must create, initialize, execute, and terminate the ImageMagick binary 1,000 separate times.
  • mogrify (Single Process Model): mogrify natively accepts multiple file arguments or wildcards (e.g., mogrify -resize 800x600 *.jpg). The operating system loads the ImageMagick binary and its associated shared libraries into memory only once, processing all specified images sequentially within the same process lifecycle.

Process Overhead and Real-World Impact

Launching an external binary incurs fixed overhead:

  1. Dynamic Linker Overhead: ImageMagick relies on numerous shared libraries (e.g., libpng, libjpeg, libtiff, libgomp, liblcms2). Every invocation of convert requires the OS dynamic linker (ld.so) to resolve and map these libraries into the process address space.
  2. Resource Allocation: Each execution requires memory allocation, thread initialization (via OpenMP), and configuration file parsing (such as delegates.xml and policy.xml).

Impact on Small vs. Large Images

  • Small to Medium Images: For small images (under 2 megapixels), the setup and teardown overhead of convert can constitute up to 50% or more of total execution time. In this scenario, mogrify can be 2x to 5x faster than a basic shell loop calling convert.
  • Large Images / Complex Operations: For large files (e.g., 50+ megapixel RAW conversions) or compute-heavy filters, pixel manipulation dominates execution time. Process overhead becomes negligible, narrowing the speed gap between the two commands.

Syntax Comparison

Batch Processing with convert (Slower)

for file in *.jpg; do
    convert "$file" -resize 50% "thumbs/$file"
done

Creates a new process for every single file.

Batch Processing with mogrify (Faster)

mogrify -path thumbs/ -resize 50% *.jpg

Creates one process that processes all files in a single execution.

Parallel Processing Considerations

While mogrify is faster than a standard single-threaded convert loop, native mogrify runs sequentially. To achieve maximum throughput across multi-core CPUs:

  • mogrify + GNU Parallel: Splitting the batch into chunks using tools like GNU parallel or xargs with mogrify combines the low process overhead of mogrify with multi-core utilization.
  • convert + GNU Parallel: Running convert in parallel mitigates the sequential bottleneck, but still incurs per-file process creation overhead.

Summary

For sequential batch operations, mogrify is consistently faster than convert due to eliminating the operating system overhead of repeated process creation, dynamic library loading, and configuration initialization.
