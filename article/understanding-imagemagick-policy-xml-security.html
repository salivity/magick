Understanding ImageMagick policy.xml Security

The policy.xml configuration file in ImageMagick is a critical security control mechanism designed to restrict system resources, disable risky file formats, and prevent unauthorized file access. This article explains the primary purpose of policy.xml, how it mitigates critical security vulnerabilities like remote code execution and denial-of-service attacks, and how administrators configure it to harden their servers against image-processing exploits.

The Core Purpose of policy.xml

ImageMagick supports over 200 file formats and delegates complex rendering tasks to external libraries. Because image parsing is inherently prone to memory-corruption flaws and parser vulnerabilities, ImageMagick uses policy.xml as a centralized security layer. It enforces operational policies that dictate what the software is allowed to do, regardless of what an input file or command requests.

The primary purposes of policy.xml include:

1. Mitigating Remote Code Execution (RCE)

Many advanced image formats (such as PostScript, PDF, EPS, and MVG) rely on external delegates like Ghostscript or internal scripting features. Attackers frequently exploit vulnerabilities in these delegates to execute arbitrary code on the host system (as seen in exploits like ImageTragick).

Using policy.xml, administrators can completely disable vulnerable or unnecessary coders using policy rules:

<policy domain="coder" rights="none" pattern="PS" />
<policy domain="coder" rights="none" pattern="EPS" />
<policy domain="coder" rights="none" pattern="PDF" />
<policy domain="coder" rights="none" pattern="XPS" />

Setting rights="none" ensures that ImageMagick outright rejects these formats, blocking exploitation attempts before the parser processes the payload.

2. Preventing Denial of Service (DoS)

Malicious users often upload "decompression bombs" or "pixel bombs"—tiny image files that expand into gigabytes of memory upon processing, exhausting server resources and causing crashes.

The policy.xml file allows administrators to set hard limits on system resource consumption:

  • Memory and Map Limits: Restrict the maximum RAM ImageMagick can allocate.
  • Disk Limits: Cap temporary disk cache usage.
  • Dimension Limits: Define maximum allowable image width and height to reject oversized payloads immediately.
  • Time Limits: Enforce maximum execution duration for processing a single image.

Example resource limit configuration:

<policy domain="resource" name="memory" value="256MiB"/>
<policy domain="resource" name="map" value="512MiB"/>
<policy domain="resource" name="width" value="16KP"/>
<policy domain="resource" name="height" value="16KP"/>
<policy domain="resource" name="time" value="120"/>

3. Restricting File System and Path Access

ImageMagick supports directives that allow indirect file reading, such as utilizing the @ prefix to read filenames from external files or using URL handlers (HTTPS, HTTP, FTP) to fetch remote resources.

Through policy.xml, administrators can disable external protocols and restrict read/write operations to safe directories, preventing server-side request forgery (SSRF) and local file inclusion (LFI) vulnerabilities:

<policy domain="delegate" rights="none" pattern="HTTPS" />
<policy domain="path" rights="none" pattern="@*" />

File Location and Precedence

The policy.xml file is typically located in system configuration directories such as:

  • /etc/ImageMagick-6/policy.xml (ImageMagick 6)
  • /etc/ImageMagick-7/policy.xml (ImageMagick 7)
  • /usr/local/etc/ImageMagick-7/policy.xml (Custom source installations)

When multiple policy files exist, ImageMagick applies the most restrictive policy found.

Conclusion

The policy.xml file is ImageMagick's primary defense-in-depth tool. By enforcing resource limits and explicitly disabling high-risk file formats and delegates, administrators can safely process user-submitted images while minimizing the attack surface of their infrastructure.
